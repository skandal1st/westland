# AXIMA Commerce Platform — практическая основа

Статус: рабочее архитектурное правило для дальнейшей разработки Westside.

## Цель

Westside — первая клиентская конфигурация общей платформы AXIMA Commerce. Новый магазин должен запускаться из той же кодовой базы без копирования проекта и без условий вида `if (client === "westside")` в доменной логике.

## Модель поставки

На ближайшем этапе используется модульный монолит:

- единая кодовая база и единый release-процесс;
- отдельное приложение и отдельная PostgreSQL-база для каждого клиента;
- один активный профиль магазина на deployment;
- `storeId` сохраняется во всех сквозных сущностях для целостности данных, аналитики и возможного будущего multi-store режима;
- клиентские отличия задаются конфигурацией, темой, контентом и подключёнными адаптерами, а не fork-веткой.

Такой подход даёт изоляцию данных и простое сопровождение, но не требует преждевременной SaaS-мультитенантности или микросервисов.

Поставка является Self-Hosted. Первоначальная настройка выполняется единым install CLI, который собирает профиль магазина, настройки email, подключения, модули и секреты, затем выполняет проверяемый bootstrap. Выбранная модель мягкого лицензирования описана в [`security/licensing-hardening/hardening.md`](./security/licensing-hardening/hardening.md).

## Слои

| Слой | Ответственность | Зависит от клиента |
|---|---|---|
| Platform runtime | запуск, БД, auth, audit, jobs, media, observability | нет |
| Commerce core | товары, категории, бренды, цены, остатки, корзина, заказы | нет |
| B2B module | компании, модерация, точки доставки, группы цен, счета | включается профилем |
| Content module | баннеры, страницы и управляемый контент | включается профилем |
| Integration adapters | 1С, МойСклад и другие внешние системы | выбирается профилем |
| Store profile | бренд, возможности, политики и bindings | да |
| Theme | tokens, assets и разрешённые layout-варианты | да |

Зависимости направлены внутрь: storefront и back office вызывают use cases платформы; адаптеры реализуют порты платформы. Commerce core не импортирует код конкретной ERP или конкретного клиента.

## Профиль магазина

Профиль — типизированная, валидируемая конфигурация deployment. Минимальный контракт:

```ts
type StoreProfile = {
  identity: {
    code: string
    name: string
    legalName?: string
  }
  modules: {
    b2b: boolean
    content: boolean
    invoices: boolean
  }
  policies: {
    catalogRequiresAuth: boolean
    registration: 'manual' | 'auto'
    requireAgeConfirmation: boolean
  }
  integrations: {
    primaryErp: 'one-c' | 'moysklad' | 'custom'
  }
  theme: {
    id: string
    defaultPalette: string
  }
}
```

Секреты и изменяемые бизнес-настройки в профиль не помещаются. Пароли и токены живут в secret/environment storage; реквизиты, ценовые группы, склады, баннеры и другие рабочие данные — в БД и back office.

## Границы конфигурации

1. **Platform defaults** — безопасные значения общего продукта.
2. **Store profile** — состав модулей, политики и идентичность deployment.
3. **Environment bindings** — БД, media storage, ERP endpoint и секреты.
4. **Runtime settings** — изменяемые сотрудником настройки магазина в БД.

При конфликте runtime-настройка может уточнять профиль только в пределах включённой возможности. Например, сотрудник может переключить ручную модерацию на автоматическую, если registration доступна, но не может включить отсутствующий модуль.

## Контракты расширения

Первый обязательный extension point — ERP:

- импорт канонического каталога;
- импорт цен и остатков по складам;
- экспорт канонического заказа;
- healthcheck, cursor, retry и reconciliation;
- внешние payload и идентификаторы не попадают в доменные модели.

Следующими портами по мере появления реальной потребности становятся media storage, уведомления, генератор документов и доставка. Абстракции не создаются заранее без второго варианта реализации или подтверждённого сценария замены.

## Правила разработки

- Не использовать название клиента в domain/application-коде.
- Не хранить клиентские цвета, логотипы, телефоны и тексты в общих компонентах.
- Не связывать способ оплаты напрямую с названием склада; использовать `FulfillmentChannel`.
- Не считать ERP источником доменной идентичности; хранить `ExternalReference` отдельно.
- Все запросы и уникальные ограничения для бизнес-сущностей должны учитывать магазин.
- События для аналитики формируются из стабильных внутренних ID и версионированных payload.
- Feature flag отвечает за поведение уже установленного модуля, но не заменяет авторизацию.
- Изменение схемы должно работать для всех поддерживаемых профилей.

## Текущее состояние Westside

Уже соответствует основе:

- `Store` и store-scoped commerce-сущности;
- канонические товары, клиенты, цены, склады и заказы;
- `FulfillmentChannel` между оплатой, складом и ценовой группой;
- `CommerceConnector`, `ExternalReference`, sync state и outbox;
- B2B-модерация, точки доставки и брендовые баннеры в модели.

Нужно извлечь из presentation-слоя в профиль/настройки:

- название Westside и metadata;
- контакты, подписи и служебные email;
- демонстрационные баннеры и брендовые цвета;
- префиксы localStorage;
- доступные палитры и theme assets;
- демонстрационные fulfillment labels и данные каталога.

## Критерий готовности шаблона нового клиента

Новый магазин считается разворачиваемым без fork, если для него достаточно:

1. создать профиль и theme assets;
2. заполнить environment bindings и секреты;
3. выполнить миграции и idempotent bootstrap;
4. настроить ERP-адаптер и соответствия складов/цен;
5. заполнить реквизиты и контент через back office;
6. пройти smoke flow: регистрация → модерация → каталог → заказ → документ → экспорт ERP.

Изменение общих исходников ради названия, цвета, контакта, склада или ERP клиента означает, что платформенная граница проведена неверно.

## Ближайшие архитектурные шаги

1. Ввести типизированный `StoreProfile` и профиль `westside`.
2. Подключить профиль к metadata, header, age gate и browser-storage namespace.
3. Перенести demo fixtures за интерфейс repository/provider, не смешивая их с production use cases.
4. Выделить application use cases регистрации, модерации, каталога и checkout из React-компонентов.
5. Сделать idempotent bootstrap магазина, складов, каналов и администратора.
6. Реализовать первый вертикальный контракт 1С только после согласования транспорта и mapping.

Каждый шаг должен сохранять работающий Westside и сопровождаться проверкой хотя бы одного полного пользовательского сценария.
