# Развёртывание AXIMA Commerce

Пошаговый runbook: выпуск лицензии, установка на сервер, проверка и день-2 операции
(обновление, бэкап, восстановление). Модель лицензии — **бессрочная, анти-копирование**,
привязанная к installation identity; активация происходит **один раз при разворачивании**,
дальше приложение проверяет grant **офлайн** (без сети и heartbeat).

Роли:
- **Издатель (вендор)** — держит приватный ключ, выпускает лицензии, поднимает сервер активации.
- **Инсталляция (сервер клиента)** — активируется один раз и работает автономно.

---

## 0. Предварительные требования

- Целевой сервер: **Linux + Docker Engine + docker compose v2**.
- На хосте установки нужен **Node.js** (для шага активации внутри `install.sh`).
- Домен, указывающий на сервер (для HTTPS через Let's Encrypt).

Для локальной **разработки лицензия не нужна**: enforcement выключен, пока не задан
`LICENSE_ENFORCE=1` (или `NODE_ENV=production`).

## 1. Сторона издателя (один раз)

```bash
# 1.1 Ключевая пара издателя. Приватный ключ — секрет, публичный раздаётся инсталляциям.
npm run license:keygen
#   → services/license-server/keys/publisher-private.pem (0600)
#   → services/license-server/keys/publisher-public.pem  (раздать клиенту)

# 1.2 Выпуск лицензии клиенту. Activation key печатается ОДИН РАЗ — сохраните его.
npm run license:issue -- --customer westside \
  --modules commerce-core,commerce-b2b,content,invoices \
  --production-seats 1 --staging-seats 0
#   → services/license-server/data/licenses.json
#   → печатает: axm_XXXXXXXXXXXXXXXXXXXX   (это AXIMA_ACTIVATION_KEY)

# 1.3 Сервер активации (нужен только в момент установки инсталляции).
npm run license:server
#   → слушает http://127.0.0.1:4010
```

`--modules` — то, что клиенту разрешено включать (лицензия только сужает набор из профиля).
`--production-seats` ограничивает число боевых активаций (защита от копирования проекта).

## 2. Поддерживаемая установка

Linux, Node.js 22+, Docker Engine и Compose v2 с `--wait`, tar; запуск от root для прав UID/GID 1001. На сервер доставляют проверенный image и deployment tooling соответствующего выпуска. Сборка и git pull на сервере больше не входят в установку/обновление.

1. Скопировать `install.config.example.json` в приватный install config, заполнить store/admin/license. Если email не настроен, задать `"email": { "enabled": false }`.
2. Загрузить проверенный образ через `docker pull registry/image@sha256:...` либо `docker load`.
3. Передать activation key и начальный пароль администратора через окружение:

```sh
# Значения передаются из защищённого окружения оператора.
export AXIMA_ACTIVATION_KEY
export ADMIN_PASSWORD
sh ./install.sh --image registry/image@sha256:... --config /private/install.config.json
# Эквивалент: npm run install:server -- --image sha256:... --config /private/install.config.json
```

Поддерживается только PostgreSQL сервиса `postgres` этого Compose. Пароль БД и NEXTAUTH_SECRET генерируются один раз; `database.urlEnv` и `outputDir` из конфигурации для этого пути заменяются управляемыми значениями. Профиль, grant и identity создаёт внутренний helper `scripts/install.mjs`; он сам по себе не устанавливает магазин. `npm run install:config -- plan --config ...` остаётся предпросмотром конфигурации без активации.

Порядок: общий lock → активация → приватные файлы/права → фиксация image ID → PostgreSQL → migrate deploy → bootstrap → app → business readiness → worker health. При обрыве активации повтор с тем же config продолжает pending installation; identity не заменяется. Прерванную установку без marker нельзя «исправлять» удалением ключей.

Повторный `install.sh --image ТОТ_ЖЕ_ID` не обращается к issuer, не меняет пароль администратора и настройки магазина. Для другого image используется только update. Mutable tags, прежние `--domain/--no-pull/--no-backup` и сборка исходников на сервере не поддерживаются.

HTTPS/nginx настраиваются отдельным эксплуатационным шагом по `deploy/nginx.conf.template`. Скрипт установки не изменяет системный nginx и не получает сертификаты. До открытия трафика проверить HTTPS, proxy headers и бизнес-сценарии R39. Локальная готовность контейнеров не означает готовность продаж.

## 3. Проверка

```bash
# Статус лицензии из артефактов на диске
node scripts/license-check.mjs \
  deployment/config/license.json \
  deployment/secrets/installation-private-key.pem \
  deployment/config/publisher-public.pem
#   → license status = ACTIVE
```

Также:
- **Health:** `GET /api/health` → `license: { status: "ACTIVE", enforced: true }`.
- **Backoffice:** раздел «Лицензия» — статус, поля grant'а, лицензированные модули.

При не-`ACTIVE` и включённом enforcement блокируются **мутации** (оформление заказов,
импорт, изменения в backoffice); витрина, чтение и health продолжают работать —
данные не портятся.

## 4. День-2 операции

### Обновление с проверкой копии и откатом

```sh
sh ./update.sh --image registry/image@sha256:...
node scripts/deploy.mjs verify
```

Скрипт работает из любой директории, использует корневой Compose и `deployment/secrets/.env`. Image должен уже находиться в локальном Docker; фактический ID сохраняется в .env с сохранением прав/владельца. App и worker обновляются вместе. Compose restart больше не запускает миграции.

Обновление удерживает общий lock, останавливает worker (до 16 минут на завершение) и app, сохраняет обязательный backup и применяет миграции к восстановленной копии БД в отдельной внутренней сети. Очереди, внешняя 1С и рабочий exchange volume к копии не подключаются. На новой схеме выполняются проверки candidate и прежнего image: лицензия/identity, модули профиля, store/settings/admin, отсутствие незавершённых миграций, чтение всех моделей через Prisma Client каждого image.

Автоматический путь принимает неизменённую историю миграций и только узкий набор новых изменений: nullable-колонки простых типов без default/constraints и обычные неуникальные индексы. Другие SQL, включая переименование/удаление, data migration и новые ограничения, требуют отдельной проверенной процедуры. Флага обхода нет. Это ограничение защищает возврат прежнего приложения, а не доказывает всю бизнес-совместимость.

Для выпуска промотоваров 23.09.2026 отдельно проверена миграция `20260923200000_gift_promotions`: новая таблица GiftPromotion и nullable поля Cart/OrderItem. В `deployment-lib.mjs` разрешён только её точный нормализованный SHA256; изменение SQL исключает её из разрешённого набора. Проверки candidate и previous image на копии БД остаются обязательными. Перед выпуском операторская библиотека на хосте обновляется из проверенной сборки с сохранением прежнего файла.

Только после PASS на копии миграции применяются к установке. Candidate app проверяется до старта worker. При отказе readiness после успешно завершённых миграций возвращаются прежние app/worker и image pin; команда всё равно завершается с кодом 1 и статусом `ROLLED_BACK`. Forward migrations остаются в БД.

Если миграция на самой установке оборвалась, автоматический запуск старого кода запрещён: `RECOVERY_REQUIRED`, оба writer остановлены, backup сохранён. Нужно восстановить согласованные DB/files по recovery runbook, затем выполнить verify. При SIGKILL/аварии хоста lock и журнал могут остаться: сначала проверить PID, контейнеры и состояние миграций; stale lock нельзя снимать вслепую. Прямые команды Docker/SQL других операторов этим lock не блокируются.

`deployment/last-operation.json` содержит этапы, image IDs и путь backup. `last-command-error.log` — приватная диагностика (может содержать технические данные), не публиковать. Бэкапы обновлений находятся в `deployment/update-backups/`; их retention/off-host хранение — отдельная задача.

Предыдущий image также должен содержать `scripts/deployment-readiness.mjs`. Переход со старого deployment tooling без этой проверки и миграции за пределами указанного контракта требуют отдельной rehearsal в R40.

### Бэкап
```bash
./backup.sh --out backups
#   БД (pg_dump) + secrets + config + media + installation identity → backups/axima-backup-<ts>.tar.gz (0600)
```

### Восстановление (в т.ч. на другом сервере)
```bash
./restore.sh --archive backups/axima-backup-<ts>.tar.gz --confirm
#   перезапись БД + возврат secrets/config/media.
```
После восстановления installation identity присутствует снова, поэтому лицензия
**реактивируется без нового seat**: перезапустите приложение **или** backoffice →
«Лицензия» → «Перечитать лицензию» (действие пишется в audit как `LicenseReactivated`).

## 5. Проверки перед выпуском

`npm run check:release` выполняет обязательные локальные проверки, полный replay разрешённого XML-набора и Docker smoke точного image. Требуются guarded test DB, Docker и `AXIMA_R16_SOURCE_DIR`.

`npm run acceptance` / `sh scripts/acceptance.sh` не выдают PASS за непроверенные backup/restore/update/rollback: после локальных проверок возвращают exit 2, пока бизнес-приёмка R39 не подключена и не выполнена (R37 уже выполняется обязательной стадией deployment-drill). Ошибка проверки возвращает exit 1. Полная инструкция и границы доказательств — [RELEASE_CHECKS](docs/RELEASE_CHECKS.md).

## 6. Диагностика

| Симптом | Причина | Решение |
|---|---|---|
| `install.sh`: activation/config error | не завершена активация | проверить приватную диагностику и повторить с тем же config и AXIMA_ACTIVATION_KEY |
| `install.sh`: `node is required on the host` | нет Node.js на хосте | поставить Node или выполнить активацию отдельно (§2) |
| `license status = INVALID (belongs to another installation)` | grant от другой инсталляции (копия) | активировать заново на этом сервере (§2) или восстановить свою identity из бэкапа |
| API отвечает `403 license_invalid` | enforcement включён, лицензия не ACTIVE | проверить `/api/health`, при необходимости «Перечитать лицензию» после восстановления |
| Auth-роуты `500 NO_SECRET` | нет `NEXTAUTH_SECRET` в окружении | `install.sh` генерирует его в `.env`; для ручного запуска задать переменную |

Архитектура лицензирования: [`docs/security/licensing-hardening/hardening.md`](./docs/security/licensing-hardening/hardening.md).


## Recovery contract (R03–R04, 20.09.2026)

Актуальные команды, содержимое manifest и ограничения описаны в [docs/RECOVERY.md](docs/RECOVERY.md). Backup кратко останавливает app и возвращает прежнее состояние запуска. Restore проверяет archive, восстанавливает данные/права и оставляет app остановленным до проверки image и health; одного reload лицензии недостаточно для открытия трафика. Новые архивы содержат exchange volume; legacy archives без manifest требуют отдельной конвертации. Нужны Node.js, tar и Docker Compose; на Linux restore запускается от root.


## Защита сессий и auth endpoints (R27–R30)

Поддерживаемая схема: один nginx → приложение, опубликованное только на loopback.
Новый nginx-шаблон перезаписывает `X-Forwarded-For` значением `$remote_addr`.
Приложение берёт последний валидный IP в XFF, поэтому совместимо и с прежним
шаблоном `$proxy_add_x_forwarded_for`. Некорректный последний адрес попадает в общий
bucket `unknown`; предыдущие элементы не используются. При добавлении CDN или
ещё одного proxy требуется отдельно настроить и проверить доверенную цепочку.
`update.sh` не обновляет установленный nginx-конфиг автоматически.

Каждое чтение NextAuth-сессии проверяет текущие статус, роль и связи пользователя
в БД. Недоступная БД, удаление, блокировка или несовпадение storeId закрывают доступ.
Проверка действует на последующие запросы; уже исполняющийся запрос не прерывается.
JWT остаётся идентификатором входа, а его прежняя роль не используется как разрешение.

Логин: максимум 5 попыток на пару IP/email и 30 попыток на IP за фиксированные
60 секунд, до обращения к БД и bcrypt. Email нормализуется, ключ содержит SHA-256.
Отклонённые попытки не продлевают окно. Успех не сбрасывает бюджет IP. Ответ сохраняет
общую ошибку credentials; глобальной блокировки аккаунта из чужой сети нет.
Лимиты находятся в памяти процесса, сбрасываются при restart и не общие для реплик.
Текущая схема рассчитана на один процесс; несколько реплик требуют общего limiter.
Регистрация сохраняет 5 запросов/минуту и HTTP 429 с Retry-After.

Ссылки баннеров: внутренние относительные пути и полные HTTP(S) URL. `null`/пустая
строка снимают ссылку. Скриптовые схемы, управляющие символы, backslash, protocol-relative
URL и пробелы отклоняются; пробел в пути следует кодировать `%20`. Старые опасные
значения остаются в БД для исправления, но не передаются как активная ссылка витрины.

Локальная HTTP-проверка требует поднятого `docker-compose.test.yml`, применённых
миграций, Docker и образа `nginx:stable-alpine`. После установки `AXIMA_TEST_DATABASE=1`
и разрешённого тестового `DATABASE_URL`:

```text
node scripts/build-worker.mjs
node --test tests/deployment/auth-security.test.mjs
```

Тест создаёт отдельный store в тестовой БД, временные ключи/профиль, Next.js dev и
nginx; затем удаляет store, останавливает приложение и удаляет nginx-контейнер.
Выбор БД проверяется тем же fail-closed guard, что и integration suite.


## Источники и поколения обмена 1С (R09/R10/R05.2)

Перед rollout этой версии обязательно привязать credentials к connection ID. Предпочтительно задать `ONEC_SOURCES_FILE=/app/deployment/secrets/onec-sources.json`; файл содержит JSON-массив `{ "connectionId": "…", "user": "…", "pass": "…" }`, по одной записи на источник, с разными логинами. Файл входит в существующий read-only deployment mount и backup секретов; в Git его не добавлять. Старый одиночный ONEC_EXCHANGE_USER/PASSWORD поддержан только вместе с явным ONEC_EXCHANGE_CONNECTION_ID. Без привязки endpoint отвечает 503. Секреты не записываются в connection.config и не возвращаются через staff API.

Параметры протокола со стороны 1С остаются стандартными: checkauth → init → file → import. Cookie обязательна после checkauth. Части файла пишутся в постоянный журнал и `onec_exchange/sources/<connection>/<session>/<file>/`. Перезапуск приложения не обнуляет приём. Повтор с теми же bytes неоднозначен в стандартном протоколе без offset: сервер возвращает `failure / ambiguous_chunk_repeat_restart_exchange` без дописывания. В таком случае начать новую сессию checkauth и повторить файл целиком. Offset/номер части от 1С не требуются. Лимиты: 20 MiB на запрос (nginx 25m остаётся совместимым), 128 MiB на файл, 512 MiB на сессию; фактическое тело проверяется даже без Content-Length.

`mode=import` проверяет и фиксирует полученный файл, но ещё не публикует каталог Commerce. В панели интеграций открыть «Файлы обмена», явно выбрать завершённые сессии одной выгрузки (каталог, предложения или оба потока) и нажать «Зафиксировать набор для импорта» (ADMIN). Затем запустить синхронизацию. Только выбранные файлы входят в неизменяемое поколение; свежие/частичные загрузки не подменяют файлы выполняющейся job. Каталог, цены и остатки данной синхронизации несут один generationId. Неполный checkpoint другого поколения даёт конфликт, а не продолжается на новых файлах.

Старые глобальные catalog/status.json и cookie v1 не используются автоматически. До первого импорта нужен новый обмен и явно зафиксированный набор; перенос legacy-файлов без проверки происхождения не выполняется. Старые ONE_C jobs без generationId запрещено автоматически привязывать к новой загрузке. Отключение/повторная активация источника меняют его revision, аннулируя старые cookie и поколения для нового запуска.

Это не готовый live cutover: freeze/drain и активация — R05.5/R14, full/delta описан в следующем разделе, автоматический runner и результаты этапов — R13/R15. Реальный сервер в ходе реализации не менялся. Проверенный порядок и ограничения: [отчёт R09/R10](docs/audits/AXIMA_COMMERCE_R09_R10_RESULTS.md).


## R11/R12/R05.3: full/delta и явные соответствия

После миграции `20260920220000_import_source_ownership` настройте соответствия источника в панели интеграций: каждый price type GUID → PriceBook с совпадающей валютой, warehouse GUID → InventoryLocation. Неизвестные типы не используют default book. POST `/api/staff/integrations/<id>/mappings` (ADMIN) принимает `{entityType,externalId,entityId}`; seller дополнительно содержит `seller` с реквизитами. PUT того же endpoint принимает `{channelId,warehouseExternalId,priceTypeExternalId,sellerExternalId}`. PREPARING хранит настройки до активации, ACTIVE применяет их к каналу.

Full разрешает удалять отсутствующие данные только при явном `СодержитТолькоИзменения="false"` и, для цен/остатков, объявленных XML типах цен/складах. Unknown и delta не очищают отсутствующие строки. Публикация допускает один поток (catalog-only / offers-only); старые XML не подмешиваются. Нулевая цена снимает предложение, нулевой остаток сохраняется. Timestamp без часового пояса считается неизвестным.

Legacy PriceEntry/Stock без provenance не присваиваются новому источнику автоматически: затрагивающий их full отклоняется. Перед rollout требуется отдельно проверенный перенос владельцев либо контролируемая перезагрузка. Смена mapping снимает предыдущие принадлежащие ему значения до следующего импорта. Поколения упорядочены по публикации; полный cross-stage rollback, нагрузочная приёмка реального ассортимента и переключение TEST → PRODUCTION ещё не готовы. Worker/lease реализованы в R14/R15 ниже. См. [результаты R11/R12/R05.3](docs/audits/AXIMA_COMMERCE_R11_R12_RESULTS.md).


## R13: результаты импорта

Примените миграции `20260920230000_import_outcomes` и затем `20260920230100_reclassify_import_failures`. Вторая использует новые enum values и не должна объединяться с первой в одну внешнюю транзакцию. Она исправляет только доказанные исторические ложные SUCCEEDED по сохранённой статистике.

Sync API возвращает runId/outcome и три стадии; 409 может означать частично применённые данные. Отчёт сохраняется в SyncRun и доступен в панели после обновления страницы. RETRYING — ожидание повтора после ошибки, PARTIAL — неполный результат, SKIPPED — стадия не исполнялась. Повтор отдельной job не запускает оставшиеся стадии и не переписывает исторический отчёт. После исправления причин запустите sync заново для полного отчёта. Crash recovery/claim и отдельный worker реализованы в R14/R15 ниже; текущий На этапе R13 HTTP-контракт запуска — 202 с ID очереди. [Подробности R13](docs/audits/AXIMA_COMMERCE_R13_RESULTS.md).


Текущий контракт R15: POST sync/retry возвращает 202 при принятии; итог success/partial/failed читается из сохранённого отчёта. Описание прежнего синхронного ответа выше относится к этапу R13.

### R14: аренда исполнения и восстановление

Миграция `20260921000000_execution_leases` добавляет lease в IntegrationJob, OrderExport и SyncRun. При внедрении остановить все старые writers, выполнить штатные миграции и запускать только новую версию: legacy RUNNING/PROCESSING без lease считаются прерванными. Не смешивать старые и новые runners.

Lease — 60 секунд, heartbeat — 20 секунд, предел исполнения — 15 минут. Просроченные попытки восстанавливаются ограниченной пачкой при следующем runDueJobs/runDueOrderExports/runSourceSync, с backoff до 60 секунд и сохранением maxAttempts. Отдельный процесс polling/recovery реализован в R15 ниже. Длительность на реальных объёмах проверяется в Q01.

Локальный fencing не отменяет уже отправленный запрос 1С. Идемпотентность внешнего заказа и неизвестный acknowledgement проверяются отдельно в R22/R23. См. [отчёт R14](docs/audits/AXIMA_COMMERCE_R14_RESULTS.md). Production rollout не выполнялся.


### R15: отдельный integration worker

После миграций `20260921010000_queued_sync_worker` и `20260921010100_sync_queue_index` запускаются оба сервиса одного image:

```sh
docker compose --env-file deployment/secrets/.env --profile full up -d app worker
docker compose --env-file deployment/secrets/.env logs --tail 100 worker
```

Sync/retry HTTP отвечает 202 с ID принятой работы. Импорт и экспорт выполняются только worker; без него очередь остаётся ожидающей. Отчёт доступен по Location из ответа и в панели. Повтор той же активной синхронизации не создаёт новую цепочку.

Worker по умолчанию опрашивает БД каждые 5 секунд (`INTEGRATION_WORKER_INTERVAL_MS`, 250–60000). Один tick исполняет максимум один импорт и один экспорт с чередованием приоритета; dependency chain и backoff хранятся в БД. Лицензия проверяется повторно при исполнении. Для локального запуска: `npm run worker:build`, затем `npm run worker`; `npm run worker -- --once` — один проход. Health: `node dist/integration-worker.cjs --health`.

Перед миграциями остановить app и worker; не запускать прежний image с новой очередью. install/update/backup/restore учитывают оба writer. Обычный Compose stop даёт worker 16 минут для drain; backup/update используют ограниченную остановку, при её превышении последующее исполнение восстанавливается по lease. Restore оставляет оба сервиса остановленными.

[Результаты и ограничения R15](docs/audits/AXIMA_COMMERCE_R15_RESULTS.md). Внедрение на сервер остаётся R40; полный update/rollback acceptance — R37/R39.


### R25: приватное хранилище счетов

Основной Compose подключает named volume `invoice_media` к `/app/.media` и
задаёт `MEDIA_ROOT=/app/.media`. Каталог образа принадлежит runtime-пользователю
UID 1001 (группа каталога 1001); новый пустой том наследует владельца и права 0700. PDF создаются
с правами 0600. При замене контейнера используйте тот же Compose project и том.
Не используйте `down --volumes` при обычном обновлении установки.

Каталог не должен находиться внутри `public` или `.next`, не должен иметь nginx
alias и не публикуется как static. Скачивание — только через авторизованный
`/api/orders/:id/invoice/pdf`: владелец заказа или сотрудник его магазина.
Ответ имеет `Cache-Control: private, no-store`. Не переносите PDF в public/uploads.

Для локального запуска можно задать MEDIA_ROOT вне публичных каталогов;
по умолчанию это `<cwd>/.media`. При нестандартном bind mount оператор должен
заранее обеспечить владельца UID/GID 1001 и права 0700. Ошибки доступа к файлам
не считаются отсутствием кэша. После исправления прав скачивание можно повторить.

Том хранит только регенерируемый кэш. Источник данных счёта — неизменяемый
Invoice snapshot в PostgreSQL. Потерянный файл восстанавливается при скачивании,
без нового выпуска и без подстановки текущих реквизитов. Равенство PDF по байтам
гарантируется сохранённым кэшем; повторный рендер может менять служебные метаданные.
Backup/restore не архивирует этот том: сохраняются данные Invoice в БД, см.
[контракт восстановления](docs/RECOVERY.md). PDF и входящие файлы обмена исключены
из Docker build context.

### R26: безопасный выпуск и перевыпуск счёта

Применить миграцию `20260922030000_invoice_issue_request` и обновить Prisma Client.
Согласованно обновить web/UI: `POST /api/staff/orders/:id/invoice` теперь требует
строгий JSON `{requestKey: UUID, expectedVersion: integer}` (0 для первого выпуска).
Старый пустой запрос получает 400. Повтор после потери ответа сохраняет оба поля;
новый намеренный перевыпуск использует новый UUID и текущую версию из списка.
Первый ответ — 201, повтор — 200; поздний повтор может вернуть status VOID и не
активирует старый счёт. Никакие реквизиты или суммы через этот маршрут не принимаются.
Проверки R26 локальные; перед production выполнить целевую приёмку точного образа.


### Постоянный EnterpriseData транспорт

При наличии deployment/config/ed.json инструменты install/update/verify включают сервис ed из того же закреплённого образа. Конфигурация доступна только UID 1001; протокольные identity, peer, номера сообщений, ACK, inbox/outbox хранятся в onec_exchange:/app/exchange/ed. Для переноса переносить БД и весь обмен одним снимком при остановленных writers. Повторное создание identity или обнуление state.json недопустимо.

ED_PORT задаёт loopback-порт хоста (по умолчанию 3318), внутренний config.port должен быть 3318. Nginx публикует прежний путь HTTPS; локальный reverse SSH tunnel для серверного ED не требуется. App, PostgreSQL, worker и ED имеют restart: unless-stopped. Проверка готовности: node scripts/deploy.mjs verify; ED дополнительно проверяет лицензию, активный источник, доступ к state и авторизованный version endpoint.

Backup останавливает ED, worker и app, затем сохраняет DB/config/secrets/exchange. Restore оставляет writers остановленными. Запуск после восстановления: docker compose --env-file deployment/secrets/.env --profile full --profile ed up -d --no-build --wait app worker ed; затем verify. Audit ED ограничен текущим журналом 5 MiB и пятью архивами. Состояние протокола автоматически не очищается: лимиты 10 000 messages/sessions, 20 000 reads и 512 MiB требуют наблюдения оператора. При ed_file_busy после аварийного убийства сначала убедиться, что единственный ED остановлен, сохранить backup и проверить journal; не удалять state или менять counters.


### Дополнительный администратор заказчика

Технический администратор сохраняется при переносе. Bootstrap создаёт только первого администратора и намеренно не создаёт повторных при повторном install. Число администраторов магазина этим не ограничено.

Для отдельной учётной записи заказчика есть операторская команда scripts/create-admin.mjs. В серверном экземпляре для приёмки она находится в deployment/tools/create-admin.mjs и доступна через read-only mount приложения. Оператор готовит закрытый JSON-файл (chmod 600) с полями email, name, password и передаёт его в stdin:

```sh
cd /root/axima-client-acceptance
docker compose --env-file deployment/secrets/.env exec -T app node /app/deployment/tools/create-admin.mjs --stdin < /root/client-admin.json
```

Пароль: минимум 12 символов, максимум 72 UTF-8 байта. Не передавать его в аргументах команды или логах. После создания убрать временный credential-файл согласно принятому порядку хранения секретов. Команда требует уже существующего активного ADMIN, добавляет отдельного ADMIN/ACTIVE и запись аудита; существующую почту отвергает без смены пароля, повышения роли или замены технического администратора. Это серверная операторская команда, публичного API повышения роли нет. Учётная запись заказчика создаётся при получении его данных; сейчас она не создавалась.

## Обновление из Git

Код передаётся через push/fetch в отдельный чистый checkout сервера. Секреты, профили, volumes и база остаются в существующем каталоге установки. Не выполнять pull поверх старого рабочего каталога с локальными изменениями.

После получения проверенного коммита: checkout --detach <полный SHA>, затем из checkout выполнить sh scripts/git-release.sh /absolute/installation. Скрипт собирает image на сервере, помечает его SHA коммита и запускает штатное обновление с обязательным backup, rehearsal и verify. Журналы сохраняются в deployment/git-releases/<SHA> внутри установки. SSH нужен только для запуска и просмотра результата; архивы приложения по SSH не передаются.
